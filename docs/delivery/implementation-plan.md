## P1：初始化方式

- 在当前仓库继续开发，保留 README、CONTEXT、docs、data 及现有 Git 状态。
- 阅读当前环境的 Sites skill，以 local-only 流程初始化全栈 starter。若初始化工具不能安全合并已有目录，先在工作区的临时目录生成，再有选择地整合源码配置；不要覆盖已有文档与模板。
- 保留 starter 的 Sites 构建集成及目录约定，不手写假的 project_id，不提前调用创建或发布工具。
- 正式代码入口随 starter 生成，当前 README 中的架构目录继续承载业务实现。
- 初始化后固定依赖和锁文件，配置必要类型检查、业务测试与本地存储集成测试入口。
- 使用本地 D1、独立测试 eventId 和开发身份；本地测试不得连接生产数据库。
- 实际命令以初始化生成的 package.json 和 Sites helper 为准，当前文档不是现成的执行脚本。

## P2：先验证四个交互问题

1. 在竖屏里是否能认出 14 位角色，尤其是姓名、队伍、占用状态。
2. 点人物再点场内位置／直接拖入是否直观；先点位置的操作是否可用，点错后能否自然移出／替换。
3. 比分键盘打开后双方姓名、输入值和确认按钮是否仍清楚可见。
4. 当前轮与历史轮、可选与本轮已参赛是否容易区分。

拖拽是点选的补充，点选保持完整可用。两者均通过相同业务命令提交，不能用人物坐标决定资格。若真实 iPhone 访问本地预览尚不可用，先验证浏览器布局并明确保留实机验收项。

## P3：核心业务顺序

1. 读取模板，构建无人员分配的初始活动；校验关联与类型数量。
2. 实现 PLANNING 草稿操作、全轮可行性、确认开赛、结束声明、比分与轮次转换。
3. 实现确认阵容／赛果版本、更正及受限撤销。
4. 将纯业务模块接到 records 的 D1 条件写入、权限和幂等处理。
5. 同时验证两个请求争抢同一人、响应丢失、旧版本提交、存储失败和重复推进。

先做到一次操作可保存且可解释，再让场景消费结果。不要为了先显示漂亮人物把规则分散到事件回调中。

## P4–P5：完整闭环

- 从一场混双开始，确认所有身份都来自场景绑定，只有比分需要键入。
- 同一轮用三个不同状态验证独立性；完成后保存的选手仍不能重复参赛。
- 特别覆盖第 6 轮自由双打使用女性导致剩余阵容无解的情况。
- 最后一轮只等待两场完成，休息区域可点击查看但无开赛／录分操作。
- 录分浮层固定 matchId，历史更正不会误写当前轮。
- 建立恢复体验后再加短动画；同步失败或 WebGL 重建不清空本机比分草稿。
- JSON 导出包含完整恢复信息；CSV 从当前有效赛果生成。
- 恢复只允许管理操作和维护窗口，不允许普通游客上传文件覆盖活动。

## P6–P7：先验证，再发布

发布前应跑完整二十场演练、至少两个会话同步／冲突测试，并在本地运行生产构建。真实 iPhone 验收按用户 2026-10-29 的最新授权后置到 Site 发布后。保留验证记录，不写没有执行过的“全部通过”。

上述可执行本地工作已有通过证据后进入 [发布清单](validation-and-release.md#sites-发布最后阶段)。版本 1 已公开部署，正式活动已准备，线上共享读写检查只用隔离活动；独立匿名浏览器内容检查待补齐，详见 [发布记录](sites-public-release-2026-10-29.md)。本地通过不替代托管验证。
