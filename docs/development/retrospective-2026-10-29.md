## 按优先级处理的发现

### 1. 检查已存在，但没有自动守门入口

基线有 lint、类型、业务／真实 D1／session 测试、构建及两套 HTTP 检查，却没有 CI 工作流或启用的 pre-commit hook。开发过程中已有类型、React lint 和生产 HTTP／SSR 失败记录；现成检查若只靠 agent 想起执行，容易漏掉。

处理：新增 [CI](../../.github/workflows/ci.yml)，直接运行已有命令，包含本地 D1、二十场 HTTP 演练和生产拒绝请求后的 SSR 回归；不另写重复业务校验，不改共享 checkout 的 hooks 配置。

完成标准：配置可解析；对应命令在隔离 checkout 执行并记录结果；没有远端运行记录时明确标为尚未触发 GitHub CI。CI 通过也不替代实机验收。

### 2. 新 thread 的入口携带历史状态，缺少按任务披露

规划时的启动 prompt 要求一次读八份文档，并写着“尚未初始化应用”。后续代码已存在，README 的部分叙述和 tests README 的固定数量也有不同时间的痕迹。直接搬完整历史会增加上下文，还可能重新做已完成工作。

处理：新增精简 [AGENTS](../../AGENTS.md)，把任务路由到现有权威文档与模块 README；新增 [工作流程](agent-workflow.md)。测试入口去掉会失效的固定数量和尚未落地的目录承诺，指向当前配置与证据。

完成标准：新 thread 能定位自己的阶段、修改 seam 和相应检查；无需先读全部历史。根入口不缓存临时地址、进程号或当前测试数量。

### 3. 并行任务共享 index、构建与本地数据库，存在互相影响的机会

当前另一个 thread 在同一主 checkout 开发。全量暂存、重装依赖、重建被占用的产物或使用同一个测试活动，都可能把另一任务纳入本次操作。过去“整仓提交”发生在用户要求提交全部既有开发时，不能变成并行任务的默认做法。

处理：本次使用独立 worktree，提交采用文件白名单；[工作流程](agent-workflow.md#与开发任务并行) 说明集成前的 dirty／staged／HEAD 核对、私有提交调整和进程归属。

完成标准：本次 commit 不含业务开发改动；集成后原任务的文件、暂存状态及运行服务保持其归属。

### 4. 运行与工具经验散落在长日志里

开发中出现过原生模块／产物锁、重复构建、未消费 POST 请求体导致后续 SSR 挂起，以及宽泛读取 thread 工具输出。它们不适合全部塞进常驻 AGENTS。

处理：将触发条件与现有回归入口放到工作流程，具体修复证据继续留在 [首次验收](../delivery/local-validation-2026-10-29.md) 与 [界面验收](../delivery/ui-game-first-2026-10-29.md)。历史读取先筛选用户确认和最终结论，再按失败展开。

完成标准：相同问题能直接定位已有说明／检查；普通任务不承担完整故障史的上下文成本。

### 5. 机械检查与语义评审需要分工

已有配置和测试能处理语法、类型及已编码的不变量；业务归属、跨层恢复语义、权限体验及球场的视觉优先级仍需要上下文判断。

处理：新增只供评审按分支读取的 [CODING_STANDARDS](../../CODING_STANDARDS.md)。其中是跨文件判断与证据要求；具体机械规则继续由现有配置和脚本承担。

完成标准：评审能指出受影响契约与证据缺口；不增加与产品文档、代码配置平行维护的规则副本。
